## Goal
A user maps the units of a search or report by region in the page's time frame, and moves between map and list keeping the filter.

## Purpose
Erik (Slack 2026-11-11) wants to see where a search's units are without exporting a CSV; the reports drilldown shows counts but not places.

## Principle
Regions are the map's zoom steps (cheap, what users know, all regions placed); facet filters read statistical_unit_facet, other filters aggregate statistical_unit by region; units that cannot be placed are listed beside the map, never dropped; the map uses the page's time frame and adds no history table or other new table until a measured need.

## Relevant details
Design session 2026-11-24 20:20-20:36 with the owner (z2qt08 notes): one map page under /reports (the search's Map button opens it with the same query string; its 'View and download' row opens /search with it). Placement: own point, else region centre, else nearest ancestor with a centre; rest listed by reason (no region, region without a centre, abroad without a place) as whole-row links to search. Time: the page's selected time frame, like the drilldown. Measured (tmp/z2qt08/regions-read-speed.log, region-ids-proto.log; load 20-30): facet by county 0.09 s, municipality 0.10 s, activity C 0.04-0.19 s; name ILIKE search grouped by region live 1.8-2.4 s (the search itself costs 2.4 s); region x unit_type id-array table 1,252 rows 12 MB, read 1.5-3 ms, intersect 63k ids 0.11 s vs join 2.25 s: kept as an option for id sets that already exist (report cell unit_ids, quality findings, saved selections), not built now. Quality checks move to public.quality_finding (rabbit, 05pe0x): a quality filter is a search parameter like any other, read through statistical_unit. Tiles: only when unit coordinates exist in bulk (10 of 3.1M today).
