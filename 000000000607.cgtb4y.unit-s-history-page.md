## Goal
A unit's history page shows its newest versions first and reads from the database only the versions it shows, so a unit with hundreds of versions opens quickly.

## Purpose
Reading and drawing every version makes a long-lived unit's history page slow and long, and the newest changes are what a user looks for first.

## Principle
The page reads from the database only what it shows, newest first; the count tells how much more there is.

## Relevant details
Before: the legal unit, establishment and enterprise history pages loaded every version from statistical_unit in one request, oldest first (getStatisticalUnitHistory in app/src/components/statistical-unit-details/requests.ts). Locally the largest unit has 25 versions (average legal unit 3); a unit changed by a monthly import gains about 12 a year. Design (owner 2026-11-16): newest first, 50 at a time; 'Show 50 older' fetches the next page (range request); heading 'Showing 50 of 312'. Dimming of repeated cells (93accb154) holds across page boundaries. The chart is summarised per year and stays as it is. Open (owner 2026-11-16 13:40, see Implementation Notes): plain paging, frame-grouped, or both. Plain paging (built) lists versions in order and pages them. Frame-grouped shows, per earlier time frame, only its first and/or last version, collapsed and expandable, and the current frame's last N; it changes the table's layout and needs one request per frame or a grouped view. Both: frame groups, with paging inside the current frame, reusing the built paging.
