# PostgREST query cardinality audit: STATBUS-462

Audit date: October 8, 2026. Scope: all production TypeScript/TSX in `app/src`, including the reference/demo page, server actions, API routes, auth infrastructure, dynamic query templates and count consumers. Tests, comments and generated database types are not executable query sites. Line references identify the query's beginning at this snapshot, not a promise that future edits retain those line numbers.

## Result and counting convention

**198 executable query templates: 176 fluent query roots and 22 raw REST/request templates. Of the fluent roots, 106 are reads, 40 are mutations and 30 are RPCs. No currently live query-composition instance silently drops or multiplies parent rows. One historical affected template, the export, contained three unsafe computed-relationship arrow projections, all fixed by `7d89a032a` before this audit. No affected site beyond the export select exists today.** The remaining mentions of that arrow form in the export source are explanatory comments, and in tests are regression inputs, not sent projections.

> **Update, STATBUS-421 S5 (2026-10-08):** the export no longer issues a PostgREST request at all. Both formats stream from the app route `/api/search/export`, which runs `COPY (SELECT ...)` as the user's role with the three names joined by `LEFT JOIN LATERAL` (`app/src/app/search/export/export-sql.ts`, tested by "joins the computed names laterally, so rows without them survive"). The export template R21 and its composer (`composeExportSearchParams`, `composeExportSelect`, `export-completeness.ts`) were removed together with the STATBUS-462 request-boundary tests that guarded them; the references to them below describe the audited state, not current code.

A template is one syntactic request site. A runtime table-name or reference-view family counts once per independently implemented site, with its possible targets listed below. The four search request methods count separately even though they share a target. Query helpers that only execute/forward a supplied URL are not extra authored queries, and callers through a Next.js proxy are counted at the actual PostgREST request site. Select composers and filter/order builders are linked separately rather than double-counted.

"Safe" means no hidden parent-cardinality change from query composition. Explicit WHERE filters, RLS visibility, HEAD/count-only requests, pagination, single-record lookups, temporal rows, mutations, and aggregate output have their named semantics. It does not mean that concurrent requests share a snapshot, that every endpoint exists in the older restored database, or that arbitrary caller-authored selects passed to a generic helper are automatically safe.

## Non-obvious evidence and verdicts

### E1: computed relationship arrows versus spread

The running stack is PostgreSQL 18.6 with the restored `statbus_local` Norway database. A token was minted with the ticket's `auth.generate_jwt(auth.build_jwt_claims(...))` command, held only in process memory and never included in this report. Read-only probes called local PostgREST at `127.0.0.1:3013`, sending `Prefer: count=exact` on each request. CSV counts use the app's quote-aware `createCsvRowCounter`, not newline counting. The harness transpiles and executes the actual `composeExportSearchParams`, using the same tax/stat identifier and employees/turnover definitions as `tmp/421-full-export-url.txt`.

| Probe | Returned rows | That response's Content-Range | Verdict |
| --- | ---: | --- | --- |
| Old three arrow projections, legal units/establishments with all three relationship IDs NULL | 0 | `*/29470` | Reproduces silent loss of the entire missing-relationship cohort, HTTP 206 |
| Actual composed export select, same cohort | 29,470 | `0-29469/29470` | All parent rows preserved, HTTP 200 |
| Stored JSON arrows only, same cohort | 29,470 | `0-29469/29470` | `external_idents` and `stats_summary` arrows are scalar and safe |
| Actual full composed export, original mixed-unit filter with no pagination | 1,976,463 | `0-1976462/1976463` | All expected rows returned, HTTP 200, 426,331,946 bytes in 20.136 s |

The three export spreads are genuinely to-one. Actual definitions dumped into `tmp/462-computed-relationships.sql` show `primary_activity_category`, `secondary_activity_category`, `physical_region`, `status`, `sector` and `legal_form` all return `SETOF ... STABLE ROWS 1` and select by the target's `id` primary key. The primary keys prevent more than one returned child, rather than relying on the `ROWS 1` estimate alone. Thus these relationships cannot multiply parents. The same six definitions are also recorded under `doc/db/function/public_<name>(statistical_unit).md`.

No select-arrow on a to-many embed exists. No spread over a to-many relationship exists. The only live spreads are the three verified to-one export relationships. No direct PostgREST `.sum()`, `.avg()`, `.count()` aggregate-select expression exists in app query composition. JSON `stats_summary->code->sum` reads an already-stored JSON value, not a PostgREST aggregate operator.

### E2: ordinary embeds and inner joins

The actual unit-history select in `components/statistical-unit-details/requests.ts:219` was run for legal unit 103502, which lacks both activity relationships and physical region. It returned its one temporal parent against `0-0/1`, with those embeds NULL, not a dropped parent. Its five embeds use the same PK-bounded functions from E1.

All import-definition embeds follow `import_job.definition_id -> import_definition.id`. The local database reports `definition_id NOT NULL`, a foreign key with `ON DELETE CASCADE`, a target primary key, and read policies with `qual = true` for authenticated, regular and admin readers on import definitions. An ordinary embed preserves a job, with at most one definition. The two `!inner` sites are:

* `atoms/import.ts:238`: waiting-for-upload jobs filtered by `import_definition.mode`. Filtering parents by mode is intentional. This is not an export or an all-jobs count.
* `components/command-palette/command-palette.tsx:228`: one job by unique slug plus required definition. Because of the NOT NULL FK and read policies, the inner embed does not silently exclude a valid accessible job. `.single()` reports an error for an unexpected empty/multiple result.

Read-only outer and inner probes each returned all 4 local jobs against their own `0-3/4` totals. These queries cannot multiply jobs because the definition target is a primary key. The FK disambiguator in `atoms/getting-started.ts:60`, `!settings_activity_category_standard_id_fkey`, is **not** `!inner`. It selects a relationship, not an inner-join policy. `external_ident_type:type_id(...)` in both inspect pages is likewise a to-one FK embed, not an arrow projection.

### E3: scalar computed fields and differing RPC/aggregate counting units

`display_name(upgrade)` and `display_state(upgrade)` return scalar `text`, not SETOF. See `doc/db/function/public_display_name(upgrade).md` and `public_display_state(upgrade).md`. Listing them in either upgrades select cannot suppress or multiply upgrade rows, even if their scalar result is NULL. A live probe received HTTP 404/PGRST205 because this restored artifact has no `public.upgrade` endpoint. This is an explicit local-artifact verification limitation, not a passing live test. No migration or restore was performed to alter the owner's Norway database.

`release_identity(text)` is a SETOF/TABLE RPC bounded by the unique upgrade commit SHA. It intentionally returns 0 or 1 identity rows. The identity parser expects that shape and checks SHA identity, rather than expecting one statistical unit per row.

`statistical_unit_hierarchy` and `statistical_unit_details` return scalar JSONB documents with nested units. The callers use a single object and validate its structure. `statistical_unit_stats` returns the enterprise root and related legal-unit/establishment rows, not just the selected unit. Its two app callers expect a stats array, and the hierarchy-stats proxy deliberately excludes establishments via `.neq("unit_type", "establishment")`. A live stats probe for legal unit 103502 returned the legal unit plus enterprise 101202, 2 rows against `0-1/2`. That difference from "one requested unit" is intentional, not accidental multiplication. It took 62.773 s, but query performance is not this ticket's transport/cardinality scope.

`statistical_unit_facet_drilldown` returns **one JSONB report**, built from pre-aggregated temporal facet rows. Its overall unit count is `SUM(available_facet.count)`, not HTTP array length, dimension length or `Content-Range`. Null dimension values contribute to the overall count but need not appear as region/activity buckets. Its caller renders the report structure without comparing bucket-array length with the overall count. The statistical-history and unit-history Highcharts RPCs likewise return one chart document whose points/series are not unit rows. Definitions were inspected in `doc/db/function/public_statistical_unit_facet_drilldown(...).md`, `public_statistical_unit_stats(...).md`, `public_statistical_history_highcharts(...).md`, and `public_statistical_unit_history_highcharts(...).md`.

Other RPCs are scalar auth/diagnostic state, image bytes, an ER document, administrative/user/reset actions or relationship-changing commands. None projects a set-returning relationship with arrows in a parent SELECT. Mutating RPCs were inspected but deliberately not invoked in this read-only audit.

### E4: row counts, totals and deliberate pages

* `search/search-requests.ts:15,40,85,125,159` parses server totals separately from a fetched page. Data requests use `count=estimated`; background HEAD requests obtain an exact count for the same filter. `atoms/search.ts:356-555` uses a total to choose forward/reverse pagination, fetching an exact count before computing a reversed tail offset. There is no claim that a page's array length equals the all-results total.
* Search output is the default `select=*`. `atoms/search.ts:930-1208` composes scalar filters, stored-JSON filters/orders, temporal bounds and page offsets, not relationship projections. The `external_idents->>...` and `stats_summary->...->sum` filter/order expressions are safe scalar JSON access. Explicit NULL/negative/prefix/range filters deliberately narrow the matching set.
* `search/export/use-statistical-unit-export.ts:230-347` compares both quote-aware CSV rows and parsed JSON rows against that very response's exact total. It refuses to save either a short or an oversized response. `export-completeness.ts:44-75` uses an exact search count only as fallback when the header lacks a total, never treating an estimate as completeness evidence. Existing completeness/counter/hook tests cover this behavior. The history export uses this same composer and downloader.
* `search/components/search-export-csv-link.tsx:79` divides received rows by expected rows for progress only. Progress percentage is not the integrity guard.
* `search/components/search-result-count.tsx:14-28` and `components/table/table-result-count.tsx:11-17` display an expected page endpoint using the total and page size. They do **not** prove the received page length, so these labels alone would not expose a future short page. No current sent search/list select has the unsafe construct. The export's equality guard, not a label, prevents silently saving an incomplete export.
* Exact-count paginated list sites include regions, activity categories, worker tasks, import jobs and per-job import data. Their count is the matching table/view rows, not the returned page size. Their plain projections or verified to-one embeds preserve those rows. Dynamic filters were inspected, including worker parent/state/queue/command, import state/description and per-job errors/warnings/action/text filters.
* Count-only sites use HEAD or `limit(0)` and intentionally return no body rows. Dashboard cards choose estimated versus exact counts and apply valid-on/unit-type/missing-field filters. Getting-started and import existence checks count matching relation rows. Temporal `legal_unit`/`establishment` tables can contain several slices of one business ID, so an unbounded temporal-table count is a **slice count**, not a deduplicated business-unit count.
* `app/api/region/route.ts:8` is an unused app proxy (no app caller found) with `head:true`; it intentionally issues a count-only PostgREST request and receives NULL body data. It should not be used as a region-row fetcher. Caller-supplied `select` is passed through, not an app-composed fixed select. It is not a live row-export defect.
* `lib/excel-reference-sheets.ts:66,201` deliberately omits blank/NULL codes and optionally selects one region version for lookup sheets. The runtime view family is activity_category_enabled, legal_form_enabled, sector_enabled, region, country_enabled, data_source_enabled, status_enabled, unit_size_enabled and legal_rel_type_enabled. These scalar code/name projections cannot multiply or implicitly suppress parents. Missing codes are explicitly filtered, not lost by a relationship projection.

## Fixes, regression guard and author guidance

The only required production row-loss fix was already committed as `7d89a032a`: three computed-relationship arrow projections became verified to-one spreads. This audit found **0 additional live instances to fix**. The existing `composeExportSelect` regression checks those spreads. STATBUS-462 adds a stronger invariant at the actual `composeExportSearchParams` request boundary: five unit-type branches, each with both empty and populated dynamic definitions, replace an unsafe inherited select, retain all three spread embeds and permit arrow projections only on the two known stored JSON columns. It checks composed select output, not source files or a retired token. Because it extracts every arrow root, it would also fail if someone switched a relationship projection to `->>code` or `->id` instead of `->>name`.

Before permanent implementation, `tmp/462-verify-invariant.cjs` observed the invariant on all five branches and confirmed a mutation to `physical_region->>code` is detected. The local absent-relationship REST probe provides the real-system counterexample the invariant prevents. Author guidance is adjacent to API architecture in `.claude/rules/frontend.md:91`: arrows versus nested embeds versus three-dot spreads, actual to-one guarantees, intentional `!inner`, counting units, exact response-count verification and where to find this audit.

Verification artifacts (no credentials): `tmp/462-query-sites.txt`, `tmp/462-fetch-count-sites.txt`, `tmp/462-ast-queries.json`, `tmp/462-ast-queries.txt`, `tmp/462-computed-relationships.sql`, `tmp/462-probe.cjs`, `tmp/462-probe-results-rerun.jsonl`, `tmp/462-probe-rerun-stderr.log`, `tmp/462-invariant-prototype.log`, and `tmp/462-export-query-tests.log`. The initial upgrade probe failure is retained in `tmp/462-probe-results.jsonl` and `tmp/462-probe-stderr.log`. The completed rerun records that unsupported endpoint and continues to the full export.

Required app gates and final ticket/commit evidence are recorded in the closing verification section below. No `cli/` file is changed, so the Go gate is not applicable.

Primary semantics reference: PostgREST's official Resource Embedding documentation (v12 to-one spread and v13 to-many-array spread), in particular its computed-relationship warning that `ROWS 1` must reflect actual cardinality, default left-embed behavior and intentional `!inner` filtering. Version-dependent to-many spread behavior was not assumed from the new documentation. No such app query exists.
