## Goal
A design, agreed with the owner, for an audit trail of manual edits: who changed what, when, as a readable diff, without slowing imports.

## Purpose
Owner 2026-11-21 09:04: 'what did user X change last week' is a different question from who last wrote a row (k5q120 A) and from frozen-frame revisions (k5q120 B). A JSONB diff per change is expensive, multiplying the load of every write, so it should cover manual changes only: batch imports would become an order of magnitude slower.

## Principle
One trail for web, REST and psql, kept in the database; imports must not become an order of magnitude slower; measure before choosing.

## Relevant details
Candidate: one append-only table audit_edit(id, at, user_id, table_name, unit_type, unit_id, valid_from, valid_until, action insert|update|remove, before jsonb, after jsonb, changed_columns text[], edit_comment), written by triggers on the *__for_portion_of_valid views (INSTEAD OF path) or by the edit RPC if qtx2xm chooses one. Diff computed from OLD/NEW of the view row, so only changed columns are kept. Imports stay unaudited per row; import_job already records who ran which file when. Open: does the trail also cover removals (hmgadt) and identifier/notes edits, which do not go through the portion views; how a user reads it (unit page tab, admin page per user); retention. Depends on how edits are routed (qtx2xm). Related: k5q120 (provenance and frozen frames).

## Notes

2026-11-21 09:10 owner: users write through the web UI, REST and direct psql with the same database role, so an audit at the UI or at the for_portion_of views misses REST and scripts. The trail must be recorded in the database, on the base tables, so every path is audited the same.

Sketch discussed (not decided): statement-level AFTER triggers with transition tables (REFERENCING OLD TABLE / NEW TABLE) on each temporal base table write ONE audit row per statement: at, current_user's user id, table, action, the keys and periods touched, and only the changed columns (diff of old vs new, set-based, not per row). Cost: one insert per statement, size proportional to what changed. Imports: when the statement runs inside an import job (the worker running as the job user, 5vxfjm), the audit row references the job (import_job id, row count) instead of copying the rows, since the job's data table and file say what came in; the user is still recorded, so marking a write as an import hides detail, not who. Reading: per unit (what changed on this unit, by whom) and per user (what X changed last week). Measure: cost of one form edit, one REST batch of 1000 rows, and a Norway monthly import with the triggers on.

2026-11-21 19:11 correction to the statement-trigger sketch: a statement trigger sees every old and new row (transition tables), so a 50,000-row update still means 50,000 before/after diffs to store; one audit row only saves the per-row insert overhead, not the payload. PostgreSQL also builds the transition tables for every statement on the table, which costs memory or temp disk proportional to the rows touched even when nothing is stored. Transition tables do not pair old and new rows; diffs must be joined on a key, and sql_saga splits change valid ranges, so pairing is not 1:1. Cheaper shapes to weigh: (1) record the fact, not the values (who, when, table, unit ids, changed columns, row count); (2) a threshold: full diff for small statements (form edits, a few rows), summary only above N rows (scripts, imports); (3) let sql_saga's executor emit the audit, since its planner already knows which pieces changed and their old values (see the provenance proposal f86twg). Measure before choosing.

2026-11-21 19:14 option 4 (owner): no separate audit table; derive 'what did X change' afterwards from sql_saga history tables (system versioning on every temporal table), queried in the background. Gains: nothing recorded twice; old values come from history; inserts cost nothing extra (history is written on UPDATE/DELETE only). Caveats: needs history on every temporal table always, so every update, delete and timeline split writes an extra row + WAL; the history row says who wrote the old version and when it ended, not who ended it, unless provenance (f86twg) stamps the new row with the writer, so 'X changed this' is read from the new row's edit_by_user_id joined to the history row it replaced; a pure removal leaves no new row, so who removed it must come from elsewhere (the removing statement's role is not on any row); queries are slow (as-of joins across tables), acceptable only as background jobs; code-list tables need history too for a faithful old picture. Not decided: owner not ready to judge; measure options 1-4 on the test slot before choosing.

Caveats for all options: (a) one user across web, REST and psql means the trail must live in the database, not the app; (b) imports must not slow down by an order of magnitude; (c) statement triggers see every old and new row, so full diffs cost in proportion to rows touched; (d) sql_saga splits change periods, so old and new rows do not pair 1:1; (e) removals leave no new row; (f) who acted is only trustworthy once the worker runs imports as the job user (5vxfjm) and provenance stamps rows (f86twg).
