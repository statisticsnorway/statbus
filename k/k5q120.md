## Goal
A design, agreed with the owner, for recording who changed which unit data, when, and through what (edit form, removal, import job), so a user can later see the trail of a unit's changes, including removals that leave no row behind.

## Purpose
Owner 2026-11-17 19:09: tracking changes is a bigger consideration than removing records (hmgadt) because it may touch every import and edit path, so it gets its own task. Today a removal through the for_portion_of view (UPDATE x__for_portion_of_valid SET id = NULL, ...) leaves no record of who removed what: the kept pieces keep their own edit_by_user_id/edit_at, and worker.base_change_log holds only unit ids and ranges (hmgadt notes 2026-11-17 11:26). Edits and imports keep only the last writer per row.

## Principle
One trail for every way data changes, not a per-form patch. Decide the model before building: system time (sql_saga add_system_versioning keeps old row versions, but not who removed a row) versus a journal of actions (who, when, what, through which job or form).

## Relevant details
Facts so far: every temporal table has edit_by_user_id, edit_at and edit_comment on the row, overwritten by the next writer; sql_saga offers add_system_versioning (history table per table, unused in StatBus); worker.base_change_log is an unlogged queue of changed unit ids and valid ranges for derivation, not an audit trail; import jobs know their user (import_job.user_id). Cost matters: Norway holds about 3.1M units, and full imports write millions of rows.
