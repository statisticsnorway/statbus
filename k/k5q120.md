## Goal
A design, agreed with the owner, for recording who changed which unit data, when, and through what (edit form, removal, import job), so a user can later see the trail of a unit's changes, including removals that leave no row behind.

## Purpose
Owner 2026-11-17 19:09: tracking changes is a bigger consideration than removing records (hmgadt) because it may touch every import and edit path, so it gets its own task. Today a removal through the for_portion_of view (UPDATE x__for_portion_of_valid SET id = NULL, ...) leaves no record of who removed what: the kept pieces keep their own edit_by_user_id/edit_at, and worker.base_change_log holds only unit ids and ranges (hmgadt notes 2026-11-17 11:26). Edits and imports keep only the last writer per row.

## Principle
One trail for every way data changes, not a per-form patch. Decide the model before building: system time (sql_saga add_system_versioning keeps old row versions, but not who removed a row) versus a journal of actions (who, when, what, through which job or form).

## Relevant details
Facts so far: every temporal table has edit_by_user_id, edit_at and edit_comment on the row, overwritten by the next writer; sql_saga offers add_system_versioning (history table per table, unused in StatBus); worker.base_change_log is an unlogged queue of changed unit ids and valid ranges for derivation, not an audit trail; import jobs know their user (import_job.user_id). Cost matters: Norway holds about 3.1M units, and full imports write millions of rows.

2026-11-21 09:04 owner design discussion (ongoing; not to be built until the owner has checked the use cases, which may show this is over-engineered).

Three separate questions, each answered by its own table, not one mechanism:
(A) Who last wrote this piece of data: edit_by_user_id/edit_at on the row, made trustworthy by sql_saga provenance (f86twg) and the import role switch (prototype 5vxfjm).
(B) What did we publish, and how was it revised: frozen frames.
(C) What did user X change last week: an audit of actions, a separate table (not decided).

Not 6NF: the Danish NSO keeps one temporal + system-versioned table per attribute; assembling a unit needs a large join over two time axes and cross-attribute rules have no row to live on. Too much for StatBus.

Frozen frames (B), current thinking:
- Freezing a frame splits the timeline at the frame's end and marks the frozen rows (a marker sql_saga treats as data, so frozen and live pieces never coalesce). History (sql_saga system versioning) is written only for marked rows, via a WHEN (OLD.<marker> IS NOT NULL) condition on the history trigger; live and previous frames pay nothing. Needs sql_saga to allow a per-table trigger condition.
- Each revision of a frozen frame (the freeze is revision 1) stores a plain copy of the frame's statistical_unit rows: no indexes, no valid_from/valid_until; keyed by frame year, revision, unit_type, unit_id. Small, and downloadable as is. Rebuilding a revision from history instead would rerun the derive pipeline as of a time (slow) and need history on every code list too, so it is not the plan.
- A revision table (frame, revision, when, by whom, why) names moments, not batches; a revision is read as of its time.
- The app shows the latest revision of a frozen frame; a menu lists the revisions and their changes, and each revision can be downloaded. No search or filtering on frozen copies: download only.
- Open: one copy table per frozen frame, or one shared frozen_statistical_unit table filtered by year and revision (owner leaning to one table).
- Open: how the app shows system time at all (nothing exists today).

Cost note: sql_saga writes history on UPDATE and DELETE only (the old row version), so inserts are unaffected and an update or delete roughly doubles its writes (row + WAL in the history table); the first import is almost all inserts, monthly delta imports and edits are mostly updates and splits. Measure before deciding on any history beyond frozen rows.
